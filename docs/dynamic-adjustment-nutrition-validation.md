## 一、总体评价

| 维度 | 评分 | 说明 |
|---|---|---|
| 热量估算公式 | 7.5/10 | BMR 用 Mifflin-St Jeor（业界推荐），但 7700kcal/kg 线性假设过粗 |
| 宏量分配规则 | 6.0/10 | 蛋白/脂肪比例基本合理，但训练日碳水差异被代码削弱、肥胖者蛋白过高 |
| 差额弥补机制 | 5.5/10 | 三模式设计聪明，但**只补热量不补宏量**是硬伤 |
| 食物搭配逻辑 | 6.5/10 | 角色池分类合理，但蔬菜非硬约束、缺奶豆角色 |
| 安全保护 | 8.0/10 | 三重 cap + 疲劳保护 + safetyFloor，设计到位 |
| **综合** | **6.3/10** | **方向正确、骨架可用，但营养级联动缺失会削弱"动态调整"的核心价值** |

**一句话结论**：机制骨架（热量级滚存 + 三模式弥补 + 安全保护）做得相当扎实，但"动态调整"目前只调了**热量**这一个维度，**蛋白质/脂肪/碳水各自的缺口没有独立弥补**——这会让减脂用户在持续蛋白缺口下流失肌肉，与APP"智能分配营养"的承诺有落差。

## 三、逐层验证

### A. 热量估算层

#### A1. BMR 公式 ✅ 合理
```
男: 10×体重 + 6.25×身高 - 5×年龄 + 5
女: 10×体重 + 6.25×身高 - 5×年龄 - 161
```
Mifflin-St Jeor 是 ADA（美国营养与饮食学会）推荐的公式，对普通人群准确度优于 Harris-Benedict。**保留。**

#### A2. 7700 kcal/kg 线性假设 🔴 需优化
```ts
// shared/index.ts:424
const dailyDeficitRaw = ((currentWeightKg - targetWeightKg) * 7700) / days;
```

**问题**：7700 kcal ≈ 1kg 脂肪是经典简化，但有三个盲区：
1. **代谢适应**：体重下降 10kg，BMR 会下降约 100-150 kcal/天（瘦体重+激素变化），用固定 `currentWeight` 算 BMR 会**高估后期减重速度**，实际天数可能多 20-30%。
2. **非纯脂肪流失**：减重初期水分+糖原流失占大头，7700 系数只对纯脂肪成立。
3. **未区分初始体脂率**：高体脂者减重效率更高，低体脂者需要更大赤字才能减同量。

**营养学建议**：
- 短期（<8周）可用 7700，但应每 2-4 周用实际体重回测修正 `dailyDeficit`
- 长期目标应引入 Hall 体重动力学模型（NIH Body Weight Planner 用的就是它），考虑代谢适应衰减
- 最低成本改进：在 `dailyDeficit` 计算后乘以 0.85 的"代谢适应系数"，或每减 5kg 体重重新调用 `calculateGoalEnergyPlan`

#### A3. 赤字 clamp(-300, 750) 🟡 基本合理
- 上限 750 kcal/天：符合 ACSM "每周减重不超过 1% 体重"的建议（对 75kg 人 = 750 kcal/天）。**合理。**
- 下限 -300：允许增重场景每天多吃 300 kcal。**合理。**
- 但建议增加**下限与体重的关联**：`max(-300, -TDEE×0.15)`，避免小体重女性增重过快。

#### A4. 热量下限 1200 🔴 性别不一致
```ts
// shared/index.ts:426 — 性别中立的 1200
const calories = Math.max(1200, Math.round(tdee - dailyDeficit));

// dynamic-plan-engine.ts:95 — safetyFloor 性别区分
safetyFloorCalories: gender === "female" ? 1200 : 1500
```

**问题**：两处下限不一致。`calculateGoalEnergyPlan` 用固定 1200 生成初始目标，但动态调整的 `safetyFloor` 是男 1500/女 1200。男性用户初始目标可能 = 1200，但动态调整却认为 1500 才安全——逻辑矛盾。

**营养学建议**：
- 统一为：男性下限 1500 kcal，女性下限 1200 kcal（中国 DRIs：轻体力成年男 2250、女 1800；减脂期最低不宜低于 RNI 的 80%）
- 女性长期 1200 kcal 偏低，建议女性下限提到 1300-1350（保证微量营养素摄入）

### B. 宏量分配层

#### B1. 蛋白质 1.8 g/kg 🟡 肥胖者过高
```ts
// shared/index.ts:427
const proteinG = Math.round(input.currentWeightKg * 1.8);
```

**问题**：
- 对正常 BMI 训练人群，1.6-2.2 g/kg 是 ISSN（国际运动营养学会）推荐区间，1.8 合理。**✅**
- 但对**肥胖者**（BMI>30），按总体重算会严重高估。例如 100kg 男性 → 180g 蛋白，实际需求约 120-140g（按去脂体重 75kg × 1.8）。
- 过高蛋白会增加肾脏负担（虽然健康人群可耐受），且挤占碳水空间影响训练表现。

**营养学建议**：
```
if BMI >= 30:  蛋白 = 理想体重(BMI=24对应) × 1.8   // 或用去脂体重
if BMI 25-30:  蛋白 = (实际体重 + 理想体重)/2 × 1.8
else:          蛋白 = 实际体重 × 1.8   // 现状
```
- 另需设蛋白上限：不超过总热量的 35%（防止生酮倾向误判）

#### B2. 脂肪 25% 热量 (min 40g) ✅ 合理
- 中国 DRIs 脂肪供能比 20-30%，减脂期取 20-25% 合理。
- 最低 40g 保证必需脂肪酸（亚油酸/α-亚麻酸）+ 脂溶性维生素吸收。**保留。**
- 建议补充：饱和脂肪 < 总脂肪 1/3（心血管保护），但这是食物选择层面，非宏量层面。

#### B3. 碳水 = 剩余 (min 80g) 🟡 训练日未加强
- 被动计算导致极低热量时碳水可能逼近 80g 下限，影响训练糖原储备和甲状腺功能（T3 转化需足量碳水）。
- **训练日碳水乘数 1.12 偏小**：腿部/背部大肌群训练日糖原消耗可达 300-400g，1.12 倍对 200g 基线只增加 24g，杯水车薪。
- ISSM 推荐：训练日 4-7g/kg，休息日 3-4g/kg，差异应为 30-75%。

#### B4. adjustMacros 反推链 🟡 代码质量+效果削弱
```ts
// dynamic-plan-engine.ts:174-213
// 计算了 trainingMultiplier → fatBaseRaw → fatBase → carbsBase → carbsG
// 然后 void 掉这些中间变量，用 carbsG 反推 fatG，再用 fatG 反推 finalCarbsG
void trainingMultiplier;  // 第200行
void carbsG;              // 第205行
```

**实测影响**（以 1800kcal、蛋白120g 为例）：
| 场景 | 蛋白 | 脂肪 | 碳水 |
|---|---|---|---|
| 训练日(×1.12) | 120 | 52 | 213 |
| 休息日(×0.88) | 120 | 64 | 186 |

方向正确（训练日高碳水低脂肪），但碳水差异仅 27g（14%），远小于 1.12/0.88 = 1.27 倍所暗示的差异。**原因是 `min(restBaseFatG*1.1, fatBaseRaw)` 限制了脂肪变化幅度，再经两次反推进一步削弱。**

**建议**：重写 adjustMacros，直接按"训练日碳水目标 = 蛋白×4 + 目标脂肪×9 + 训练日碳水×4 = 热量"正向计算，而非反推。

### C. 差额弥补层（核心特色）

#### C1. 仅热量级差额 🔴 最严重问题
```ts
// dynamic-plan-engine.ts:116-136
const foodDelta = ... // 仅 calories
const trainingDelta = plannedCalories - actualCalories;  // 仅 calories
const netDelta = foodDelta + trainingDelta;  // 热量级汇总
```

**问题**：PRD 第 7.2 节明确设计了"营养余额"（蛋白/脂肪/碳水各自缺口），但实现只做了热量级。

**营养学后果**（场景化）：
> 用户今天计划蛋白 130g，实际只吃了 80g（少 50g = 200kcal），但碳水多吃了 200kcal。
> 热量差额 = 0 → APP 判断"达标"，不触发弥补。
> 实际：蛋白缺口 50g 持续 3 天 → 肌肉流失风险显著上升。

**这是减脂期最危险的盲区**——热量达标 ≠ 营养达标。减脂的核心是"保肌肉、减脂肪"，而保肌肉靠的是蛋白质，不是总热量。

**营养学建议**：
```ts
// 新增宏量级滚存
type MacroLedger = {
  proteinDelta: number;  // 蛋白缺口独立滚存，优先弥补
  fatDelta: number;      // 脂肪缺口（仅过低时告警，不强制补）
  carbsDelta: number;    // 碳水缺口（训练日前置补足）
};
// 弥补优先级：蛋白质 > 碳水 > 脂肪
// 蛋白缺口连续 2 天 > 20g → 次日强制增加蛋白食物推荐
```

#### C2. 三模式弥补设计 🟢 合理
- `extend-deadline`：适合不想改饮食的用户，顺延天数
- `repay-by-days`：适合想按期完成的用户，分摊赤字
- `hybrid`（默认 50%）：折中，避免单日剧烈波动
- **设计聪明**，给了用户选择权。**保留。**

#### C3. 上限保护 min(400, 20%, safetyFloor) 🟢 合理
- 400 kcal/天：符合"单日补偿不超过 TDEE 15-20%"的实践
- 20% 比例：防止低热量用户补偿比例过高
- safetyFloor 兜底：保证不跌破生理下限
- **三重 cap 设计到位。**

#### C4. 疲劳≥4 强制 extend-deadline 🟢 优秀设计
```ts
// dynamic-plan-engine.ts:137-144
const highFatigue = settings.training.fatigue && fatigue >= 4;
const adjustmentMode = highFatigue && netDelta > 0 ? "extend-deadline" : requestedMode;
```
**这是整个机制最亮眼的点**——疲劳累积时拒绝继续压摄入，改为顺延。符合运动科学"恢复优先"原则。**强烈保留。**

#### C5. 跨天滚存仅展示不自动改 🟡 违背承诺
```ts
// calorie-debt-ledger.ts — runningNetCalories 累加，但只返回统计
// 实际改写需用户在 atonement.tsx 页面手动确认 adjustedDailyCalories
```

**问题**：用户开启 `dynamicAdjustmentEnabled` 期望"自动调整"，但实际只是"展示建议 + 手动确认"。这会让用户觉得"开了开关没用"。

**建议**：
- 提供"自动应用"子开关（默认关，用户可选）
- 或在差额 > 阈值（如 200kcal）时主动推送通知"建议明日调整至 XXX kcal，点击应用"

### D. 食物搭配层

#### D1. 角色池分类 🟢 基本合理
`protein / staple / vegetable / fruit / fat / drinkSnack` —— 覆盖了中餐正餐的主要组分。

#### D2. 蔬菜非硬约束 🔴 需修复
```ts
// meal-planner-solver.ts:115 — pickNext(pools.vegetable) 可空
```
**问题**：蔬菜池为空时直接跳过，不报错。中餐正餐缺蔬菜是普遍营养问题（膳食纤维、维生素、钾镁缺乏）。

**营养学建议**：
- 正餐（午餐/晚餐）强制至少 1 份蔬菜（150-200g），蔬菜池为空时阻断并提示"请先在菜单添加蔬菜"
- 早餐可豁免（中餐早餐以主食+蛋白为主）

#### D3. 缺奶制品/豆制品独立角色 🟡 中国膳食指南缺口
中国居民膳食指南（2022）建议：**每天 300g 奶 + 25g 大豆/坚果**。当前角色池没有独立"奶制品"和"豆制品"角色，它们被混在 protein 池里，无法保证每日摄入量。

**建议**：新增 `dairy` 和 `legume` 角色，或对 protein 池增加"奶源占比≥1/3"的软约束。

#### D4. 烹饪油独立处理 🟢 好设计
`cookingOilFood` 作为脂肪补足源，经 `addCookingOilTowardFatTarget` 注入——这是处理中餐"隐形脂肪"的合理方式。

**但**：记忆显示已新增 `cookingMethod`（12种）字段，需确认 solver 是否根据烹饪方式调整吸油率（油炸+15%、炒+5%、蒸0%）。若未用，是数据层面的浪费。

#### D5. 每餐选4角色（蛋白+主食+蔬菜+脂肪） 🟡 偏简化
- 缺水果角色（水果通常加餐，合理）
- 但中餐正餐常含**2-3个蔬菜**和**1个汤**，当前"每餐1蔬菜"偏简单
- 建议：午餐/晚餐允许 2 个 vegetable slot

## 四、场景化验证（5 个典型场景）

### 场景 1：蛋白缺口被热量达标掩盖 🔴
**设定**：男性，80kg，目标 75kg，60天。计划蛋白 144g/天。
**实际**：今天蛋白只吃 90g（少 54g），碳水多吃 216kcal（+54g）。
**APP 行为**：热量差额 = (90×4 + 多余碳水) - 1440 ≈ 0 → 判定达标，不弥补。
**营养后果**：蛋白缺口 54g 持续 → 氮平衡负值 → 肌肉流失。减脂变减肌。
**应做**：蛋白缺口独立滚存，次日推荐增加高蛋白食物（鸡胸/鸡蛋/牛奶）。

### 场景 2：腿部训练日碳水不足 🟡
**设定**：训练日，腿部训练，计划碳水 220g。
**APP 行为**：碳水 ×1.12 = 246g（比休息日多 26g）。
**营养实际**：腿部训练糖原消耗 300-400g，246g 远不够，训练表现下降，恢复变慢。
**应做**：腿部/背部训练日碳水乘数应 1.3-1.5，或按训练部位差异化。

### 场景 3：连续 3 天未达标累积 🟡
**设定**：每天多吃 300kcal，3 天累积 +900kcal。
**APP 行为**：hybrid 模式补 50% = 450kcal，分 5 天每天 90kcal → 热量减 90/天。
**问题**：滚存仅展示，需用户手动去 atonement 页面确认。用户可能不看。
**应做**：差额 > 200kcal 时主动推送，或提供"自动应用"开关。

### 场景 4：女性用户长期 1200kcal 🔴
**设定**：女性，55kg，目标 50kg，30天。
**计算**：BMR ≈ 1250，TDEE(1.45) ≈ 1813，赤字 = (5×7700)/30 ≈ 1283 → clamp 750。
**目标热量** = max(1200, 1813-750) = 1063 → 被 1200 兜底 = 1200。
**蛋白** = 55×1.8 = 99g（396kcal，占 33%）。
**问题**：
- 1200kcal 长期偏低，女性 RNI 约 1800，80% = 1440 才是安全下限
- 蛋白占 33% 接近上限，碳水仅 1200-396-脂肪360 = 444kcal = 111g，训练日不够
**应做**：女性下限提至 1300-1350，或按"RNI×80%"动态计算。

### 场景 5：储备食物缺蔬菜 🟡
**设定**：用户菜单只有鸡胸、米饭、鸡蛋，无蔬菜。
**APP 行为**：`pickNext(pools.vegetable)` 返回空，跳过，生成"鸡胸+米饭+鸡蛋"三餐。
**问题**：无膳食纤维、维生素 C/K、叶酸，长期营养失衡。
**应做**：蔬菜池为空时阻断并强提示"建议添加菠菜/西兰花/番茄等蔬菜"。

## 六、优化建议（按优先级）

### P0（营养健康必需，建议 1-2 周内修复）

1. **宏量级差额滚存**

   - 蛋白缺口连续 2 天 > 20g → 次日推荐强制增加高蛋白食物
   - 碳水缺口在训练日前置补足（前一天多分配 10-15%）

2. **热量下限统一 + 性别区分**
   ```ts
   const safetyFloor = gender === "female" ? 1300 : 1500;
   const calories = Math.max(safetyFloor, tdee - dailyDeficit);
   ```

3. **7700 系数加代谢适应修正**
   ```ts
   // 每 5kg 体重下降，赤字效率衰减 10%
   const weightLost = startWeight - currentWeight;
   const adaptationFactor = Math.max(0.7, 1 - weightLost * 0.02);

   ```

4. **蛋白按 BMI 分档**
   ```ts
   const bmi = weight / (height/100)**2;
   const refWeight = bmi >= 30 ? 24 * (height/100)**2 : weight;
   ```

## 八、结论

**动态调整机制的"骨架"是扎实的**——三模式弥补、疲劳保护、三重 cap、热量闭合，这些设计在同类 APP 中算得上用心。但"血肉"还缺关键一块：**营养级（宏量级）的动态调整**。目前只调热量这一个维度，对减脂用户最大的风险"肌肉流失"没有防护。

最值得肯定的是 **疲劳≥4 强制 extend-deadline**，这是少见的"懂运动科学"的设计。

最需要紧急修复的是 **蛋白缺口不弥补 + 女性下限偏低 + 7700 线性假设**，这三项直接影响用户健康和减脂效果。

修复路径建议：P0 三项（1-2 周）→ P1 四项（2-4 周）→ P2 五项（4-8 周），即可将机制从"热量级动态调整"升级为真正的"营养级智能分配"。
