## 一、Phase 2 · 跨维度冲突收敛

以下 6 组冲突是汇编时发现的「同一根因、多个维度都在报」的问题，需统一收口而非各修各的。

### C1 「易记录 UX」vs「数据专业度」—— 最根本的矛盾
- **冲突双方**：UX（P2/P4 主张简化、不采集组数、渐进披露）↔ 运动数据（🔴#1 要求组数×次数×重量结构化录入）↔ 营养（🔴 要求摄入/消耗时间曲线）。
- **本质**：产品想"记一笔只要 10 秒"，但专业健身/减脂用户要"可量化、可复盘"的数据。两头都合理，硬砍任一方都会伤另一端。
- **统一收口方案（分层录入 + 渐进披露）**：
  - 饮食/训练保留"快速模式"（自然语言 + 分钟）作为默认路径，**不强制**结构化；
  - 在单条记录内提供"高级/详细"展开（饮食：单食物 kcal 微调；训练：单动作行录 组数×次数×重量kg），默认收起；
  - 看板层始终展示量化汇总（时间曲线、训练量 tonnage、完成率），让"简单记"和"专业看"各取所需。
- **关联修复**：运动 #7（自由文本解析把组/次/kg 数字删掉）是 C1 在后端的表现，须一并解——解析时保留结构化对象而非剥离。

### C2 首页"记饮食"两套餐次控件语义冲突（已闭环，可直接落）
- **冲突双方**：UX P2 ↔ 交互 #8（**同根**，UX 现象 + 交互逐行代码确认）。
- **代码硬证据**：`app/(tabs)/index.tsx` L774–783 餐次胶囊 `onPress={() => setDishRecognitionMeal(slot.id)}`（仅切"识别归入哪一餐"）；L845–858 `MealRecordCard` 箭头是真正的逐餐编辑；L784 与 L833 两个 `openDishImagePicker` 入口重复；`PillButton`≈L2008 高 30px / 11pt。
- **收口方案（已实现草图）**：把"识别归入 X"移入「今日餐次」卡每行右侧「识别归入：X ▾」控件（命中区 ≥40px + hitSlop，选中行高亮、Toast 反馈）；首页只留 1 个「AI 识别菜品」入口。详见交互侧 P2 实现草图。

### C3 语义色体系混乱
- **冲突双方**：视觉自审（warn 粉红 / amber 黄 双警示色并存）↔ 营养（青色 accent 被多义复用，致"青=? "歧义）。
- **统一收口方案**：
  - 警示色**只留一个**作主警告色（建议 amber 黄用于"超额/警告"，warn 粉红降级为"危险/临界"或合并）；
  - 营养素绑定**固定身份色**：热量=青(accent)、蛋白=紫(accent2)、脂肪=黄(amber)、碳水=绿(positive)，全 APP 同一指标永远同色（呼应营养 Issue 5 与来源详情减法）；
  - 在 `tokens.ts` 增加一份"语义色→用途"映射表，禁止同一色跨语义复用。

### C4 进度条语义不一致 + 死组件
- **冲突双方**：视觉自审（BulletChart 目标恒在右端 vs MetricCompareBar 目标随位置，语义冲突）↔ 运动 #6（BulletChart / CompactTrainingMetric 定义后零引用）↔ 视觉（DashboardGrid 含宏量环能力却零引用）↔ 营养 #20（宏量无占比/构成可视化）。
- **统一收口方案**：
  - **退役 `BulletChart`**（目标标记写死 x1=100 是 bug 且零使用），其"并列目标 vs 实际"职责由 `MetricCompareBar` + 未来训练看板承担；
  - 把 `DashboardGrid` 的 **rings（宏量环）** 接入饮食看板，一举解"宏量无占比图"（营养 #20）与"死代码"（视觉）；
  - `CompactTrainingMetric` 用于新建训练看板小指标（运动 #6）。

### C5 全站 44px 命中区准入
- **冲突双方**：交互 #1（SelectChip/Button/Switch/CollapsibleCard 全 <44px）↔ 交互 #2（识别标签 22px）↔ 交互 #8（餐次胶囊 30px）→ 跨维度共病，覆盖所有主流程。
- **统一收口方案**：把 **44px 设为 bento 控件库硬性准入标准**（SelectChip md 38→44 / sm 32→40；Button 补 hitSlop 补足到 44；Switch 外层 minHeight:44 + hitSlop；折叠按钮 32→44）。C2 的餐次控件命中区一并在此收口。

### C6 核心概念命名错位（独立项）
- **冲突**：同一机制在底部 Tab 叫"弹性"、设置里叫"动态调整"、代码/计划语义叫"弥补(atonement)"。
- **收口方案**：统一为"弥补 / 弥补账本"（"弹性"降为副标题解释词），Tab / 页标题 / 设置项三处完全一致；首次进入用一句话气泡说明用途。

## 二、Phase 3 · 完整问题清单（按优先级）

每条格式：所在界面/元素 · 现象 · 专业依据 · 改进建议 · 优先级 · 预计影响 · 来源维度

### 🔴 高（7 条）

**R1 — 首页"记饮食"两套餐次控件语义冲突**
- 界面：`app/(tabs)/index.tsx` 饮食记录卡餐次胶囊(L774–783) + 今日餐次卡箭头编辑(L845–858) + 两个「AI 识别菜品」按钮(L784/L833)
- 现象：胶囊只切"识别归入哪一餐"却长得像"点一下记该餐"，点击无反馈；同屏两套"餐次"控件语义不同；命中区 30px<44px；两处识别入口重复。
- 依据：操作习惯匹配 + 一致性 + 防错（44px 基准）。新手易误判"点了午餐为啥没记录"→ 误以为功能坏，直伤主流程。
- 建议：识别归入移入餐行「识别归入：X ▾」；首页只留 1 个识别入口；控件 ≥40px + hitSlop + Toast 反馈。已有实现草图。
- 影响：体验（首餐即挫败）、转化（饮食记录完成率↓）、留存（早期弃用）。
- 来源：UX P2 + 交互 #8（已闭环）

**R2 — 核心概念"弹性"命名与"弥补"心智错位**
- 界面：底部 Tab"弹性" / `atonement.tsx` 标题 / `more.tsx` 设置项"动态调整"
- 现象：同一"热量差额跨天弥补"机制三处三名；"弹性"抽象，减脂新手无法预判点进去是"热量账本/差额弥补"。
- 依据：心智模型一致性。核心卖点（动态弥补）被发现率/理解率双低。
- 建议：统一"弥补/弥补账本"，三处一致；首次进入气泡说明；该页把"规则"与"账本"分层（规则默认收起）。
- 影响：体验（卖点看不懂）、转化（弥补功能使用率↓）、留存（首周少用能降长期留存）。
- 来源：UX P1

**R3 — 训练记录缺失「组数×次数×重量(kg)」结构化录入**
- 界面：`components/training/ActualTrainingInputSection.tsx`（自由文本 L42–49、重量仅 3 档 L34–38、无组/次/kg 字段）；`train.tsx` L289–300 无负荷入参；`features/today-plan.ts` caloriesByMet L315–317 仅 MET×体重×时长
- 现象：只能录"文本 + 总分钟 + 定性重量(轻/中/大)"，无法录"卧推 5×5 80kg"；自由文本里的组/次/kg 还被解析剥离（见 G2）。
- 依据：增肌/力量用户靠"容量=组×次×kg"追踪进步(progressive overload)。当前把抗阻还原成"有氧分钟数"，无法算训练量、无进步曲线。
- 建议：新增"动作行"=动作名+组数+次数+重量kg（带推荐模板）；consumption 改基于 tonnage+MET；store 增 sets/reps/weightKg 数组；解析加结构化分支。
- 影响：体验（专业用户首因挫败）、转化（抗阻人群留存/付费意愿低）、留存（无训练量趋势失动力）。
- 来源：运动 #1

**R4 — 训练计划 vs 实际无「计划 vs 完成」对照**
- 界面：`TrainingPlanOverview.tsx`(L12–24 仅计划, L57 跳/plan) + `train.tsx` L188–190 未合并 actualTraining；`plan.tsx` L139–147 同
- 现象：周历只显"今天计划练胸·高碳"，无"计划45min/实际30min/完成67%"；日期格无 已完成/未做/部分完成 状态。
- 依据：计划遵从率(adherence)反馈是训练纪律核心；无对照则计划形同摆设。
- 建议：TrainingPlanOverview 叠加 actualTraining 状态徽标；点当天展开"计划↔完成"抽屉；WeekDateRailItem 增 actualStatus 字段。
- 影响：留存（遵从率可视化是训练类核心粘性）、体验（需明确"跟没跟上"反馈）。
- 来源：运动 #2

**R5 — 热量账本缺「摄入 vs 消耗」时间曲线**
- 界面：`components/CalorieLedgerPanel.tsx`（仅当日摄入 MetricCompareBar + 宏量徽章 + 文字行，**无时间曲线图**）
- 现象：用户看不到一天内"什么时段吃了多少、消耗多少"的走势，只有静态汇总。
- 依据：时间序列是减脂复盘最直觉的视图；缺曲线则"今天哪顿吃超了"不可见。
- 建议：在账本面板加一条「摄入/消耗」双线时间曲线（按餐次或按小时）；与饮食首页环卡呼应。
- 影响：体验（复盘直觉性）、转化（复盘功能使用率）、留存（日复盘习惯难养成）。
- 来源：营养 🔴

**R6 — 全站选择/开关类控件命中区系统性 <44px**
- 界面：`SelectChip.tsx`(md38/sm32)、`Button.tsx`(md42/sm34)、`Switch.tsx`(md26/sm22)、`CollapsibleCard.tsx`(折叠钮32)
- 现象：全部 <44px 基准且未设 hitSlop；SelectChip 用于性别/目标/部位多选，Switch 用于布尔数据开关——误触会无二次确认改数据。
- 依据：Apple HIG / Material 建议 44–48px（菲茨定律）。
- 建议：SelectChip md→44/sm→40；Button 补 hitSlop 补足 44；Switch 外层 minHeight:44 + hitSlop；折叠钮 32→44。**升为 bento 控件库硬性准入标准**。
- 影响：体验（单手/大屏误触率↑）、转化（Onboarding 多选完成率↓）、留存（重复误操作削信任）。
- 来源：交互 #1（覆盖面最广、修复成本最低）

**R7 — 识别食物标签 Badge 可点区过小且无反馈**
- 界面：`ActualFoodInputSection.tsx` 识别结果 `<Pressable><Badge size="sm">`（sm 高 22px，无 height/padding/hitSlop/按压态）
- 现象：这是"修正识别热量"的主入口，22px 极易点空且无按压反馈→用户怀疑"点到没点到"。
- 依据：状态可见性 + 高频精确点击。
- 建议：PressableAnimated 包裹，minHeight≥40、paddingVertical≥8；标签改 size="md"；补 accessibilityRole/label。
- 影响：体验（核心修正动作难点中）、转化（饮食记录准确率↓→计划有效性↓）、留存（主流程卡顿、日活掉）。
- 来源：交互 #2

### 🟡 中（22 条）

- 界面：`index.tsx` 首屏（环卡+记录卡[默认展开]+餐次卡[默认展开]）、"储备食物/实际饮食"双模式；`DashboardMetricDetailModal` 内 3 mode×2 groupBy 多维切换

**M3 — 新手引导单屏字段过多 + 泄漏开发注释**
- 界面：`onboarding/body.tsx`（性别/年龄/体重/身高/目标体重/周期/主要目标/目标体型/高级数据/图片），含"这三项原来在…现在合并…"内部注释
- 现象：单屏塞大量字段；直接展示内部开发说明；"目标体型"用"马甲线隐约可见"等让用户自评。
- 依据：新手上手难度 + 专业感。注释泄漏暗示"界面还在合并中"。
- 建议：删内部注释改引导句；目标体型设为可选+示例图；高级数据标注"可跳过"；可行则拆分"身体基线/目标"为两步。
- 影响：体验（引导完成率低）、转化（引导完成率=激活率）、留存（引导弃用≈高弃用）。
- 来源：UX P5

**M4 — "历史/回顾"入口分散，含死路由**

- 依据：信息架构——"回顾"应单一一致入口。
- 建议：收敛为单一"日历/回顾"入口（底 Tab 或首页固定）；弥补页专注规则+今日账；删除/复用孤立 calendar 路由。
- 影响：体验（找不到回顾）、留存（复盘习惯难养成）。
- 来源：UX P6

**M5 — "我的"Tab 实为设置页 + 暴露开发工具**

- 影响：体验（标签误导、误触）、留存（误清数据致差评）。

**M7 — 动作卡主点无响应，"加入今日参考"藏长按菜单**
- 界面：`exercise-library/index.tsx` `LibraryExerciseCard` `onPress={()=>{}}`(L418)；"加入今日参考"仅在长按菜单(L329–335)
- 现象：卡片点击空操作；库→今日训练参考的关键动作需长按；首触无可发现入口。
- 依据：可发现性——主操作应有可见 affordance。
- 建议：卡片给可见"＋加入今日参考"按钮/图标（或单击即加入+反馈）；长按仅留收藏/置顶/置底。
- 影响：体验（库到训练连接断点）、转化（动作库→今日参考转化率）、留存（训练页粘性）。
- 来源：UX P10

**M8 — 训练消耗"不叠加 TDEE"致赤字失真与信任落差**
- 界面：`train.tsx` L100–102 balance=intake−tdee(训练消耗未进)、L408"只做完成度参考，不重复叠加"、L414–461 getTrainingEnergyCopy 基于 TDEE 基线；`today-plan.ts` estimateTodayWorkoutCalories 已并入 TDEE
- 现象：计划训练计入 TDEE，但"实际训练 X kcal"醒目徽标不影响赤字；多练无额外回报、少练不恶化，数字自相矛盾。
- 依据：避免与 TDEE 内计划活动双重叠加在工程上合理，但呈现割裂致"训练不计分"错觉，屏蔽真实能量平衡信号。
- 建议：EnergyMetric 旁拆分"基础日耗(含计划)/实际训练额外消耗"两行，把"实际−计划"差值以 +/− 并入平衡；或徽标下加小字"已计入目标，未重复叠加"。
- 影响：留存（训练"不计分"感降记录意愿）、信任（数字矛盾损专业感）。
- 来源：运动 #3

**M9 — 休息日/恢复日数据矛盾与缺位**
- 界面：`train.tsx` L183 isRestDay；L192–209 RestDaySummary(仅两静态数)；L289 渲染条件 `status!=="missed" && !isRestDay`（isRestDay 时即使切 done 也不出输入区）；L313–315 文案诱导"可补充"却无入口
- 现象：休息日点"已记录训练"后文案说可补充，但录入区永不出现→"点了没反应"；恢复日看不到散步/拉伸轻活动。
- 依据：恢复日 NEAT 有数据价值；既禁止录入又诱导录入是明确 UX 矛盾。
- 建议：isRestDay 仍允许 done 展开轻量化录入（或独立"恢复日活动"入口）；RestDaySummary 显"今日活动消耗 X kcal"；改误导文案。
- 影响：体验（点了没反应=bug感）、留存（恢复日空洞拉低看板完整度）。
- 来源：运动 #4

**M10 — 动作库无组次重量处方，难当训练编程参考**
- 界面：`exercise-library/index.tsx` L403–425 + `LibraryExerciseCard.tsx`(仅 GIF+名，riskLabel.slice(0,2) 截断"高风")；训练页 `ReferenceExerciseCard` 同样无"建议组×次×重量"
- 现象：浏览动作库/参考只能看 GIF+名，看不到"建议几组几次多重 RM 难度"；缺 GIF 时占位纯"GIF"无文字兜底。
- 依据：动作库核心价值是"照着练"，新手需明确处方(3×10, RPE7)。
- 建议：卡片加"推荐 3×10·自重/RM"或难度星；缺 GIF 降级显示要点文字；risk 用完整词。训练参考卡同样补组×次。
- 影响：转化（新手照练门槛降）、体验（库实用度↑）。
- 来源：运动 #5

**M11 — 训练看板/趋势指标整体缺位（死组件）**
- 界面：`BulletChart.tsx`(定义后零引用)、`CompactTrainingMetric.tsx`(零引用)、`calendar.tsx`(grep 训练字段 No matches，纯饮食)
- 现象：成熟"目标 vs 实际"组件被饮食独占；训练侧无任何趋势/汇总看板，日历不展示训练；练一个月无处回顾进步。
- 依据：训练类 APP 留存高度依赖"进步可见性"(训练量曲线/PR/依从率)。
- 建议：新建训练看板区块用 BulletChart→改 MetricCompareBar 并列 6 项(周训练天数/量/时长/完成率/肌群覆盖/赤字达成)；日历每格叠实际训练状态(呼应 R4)；CompactTrainingMetric 用于看板小指标。
- 影响：留存（进步可视化是第一驱动）、转化（进阶用户为看数据付费）。
- 来源：运动 #6 + 视觉(死组件)

**M12 — 进度环中心数字与环比例语义不一致**
- 界面：`ProgressRing.tsx`(中心 value 显示) + 饮食首页环卡
- 现象：环按"摄入/目标"比例绘制，中心数字有时是绝对值、有时是百分比，用户分不清"环满=达标"还是"数字=剩余"。
- 依据：数据-视觉一致性。双编码不一致制造误读。
- 建议：中心固定显示"当前值 / 目标值"(如 1200/1500) + 环表示比例，统一口径；超 100% 用 amber 且中心显示"超 X"。
- 影响：体验（误读进度）、转化/留存（中）。
- 来源：营养 🟡

**M13 — 宏量无占比/构成可视化**
- 界面：饮食看板仅宏量徽章文字，无占比环/堆叠条；`DashboardGrid.tsx` 的 rings(宏量环)能力零引用
- 现象：蛋白/碳水/脂肪占比看不见，用户不知"今天碳水吃超没"。
- 依据：宏量构成是减脂核心监控项，应一眼可见。
- 建议：接入 `DashboardGrid` 的 rings 作为宏量环（呼应 C4），或用堆叠条展示三者占比 + 各自达标线。
- 影响：体验（宏量不可视）、留存（饮食纪律难建）。
- 来源：营养 🟡 + 视觉(死代码)

**M14 — 两张营养表列序与颜色编码不一致**
- 界面：首页环卡"营养来源详情"弹窗 vs 弥补页"热量账本"表
- 现象：同是"热量/蛋白/脂肪/碳水"，两表列顺序不同、颜色映射不同，用户跨页需重新认色。
- 依据：一致性——同类数据应同序同色。
- 建议：统一列序(热量→蛋白→脂肪→碳水)与身份色(见 C3)；在 tokens 固化映射。
- 影响：体验（跨页认知成本）、转化（中）。
- 来源：营养 🟡

**M15 — 语义色复用歧义 + 双警示色并存**
- 界面：全局 SemanticColor（accent 青 / accent2 紫 / positive 绿 / warn 粉红 / amber 黄）；青色被多处复用
- 现象："青色=?"在不同处含义不同；warn(粉红)与 amber(黄)两个警示色并存，用户不知哪个更严重。
- 依据：语义色应一一对应、警示色需有清晰等级。
- 建议：见 C3——警示色只留一个主警告(amber)，warn 粉红合并或降为"危险"；营养素绑定固定身份色，全 APP 同指标同色。
- 影响：体验（认色成本）、信任（中）。
- 来源：营养 Issue5 + 视觉

**M16 — 两套进度条语义冲突**
- 界面：`BulletChart.tsx`(目标竖线恒 x1=100) vs `MetricCompareBar.tsx`(目标标记随实际位置移动)
- 现象：同是"实际 vs 目标"，两套组件的"目标"呈现语义不同，团队内易用错、用户易混。
- 依据：可视化隐喻一致性。BulletChart 目标写死右端本身是 bug。
- 建议：见 C4——退役 BulletChart（修复其 bug 无意义因零使用），统一用 MetricCompareBar 语义(目标为固定参考线，实际为填充)。
- 影响：体验（一致性）、维护（去重）。
- 来源：视觉

**M17 — CollapsibleCard 折叠体写死 2000px + 收起缺 pointerEvents**
- 界面：`components/bento/CollapsibleCard.tsx`(maxHeight interpolate [0,1]→[0,2000])
- 现象：内容超 2000px 被裁剪且无法滚动；收起时 opacity=0 但子元素仍在布局，可能"幽灵点击"。
- 依据：可发现性/防错。
- 建议：onLayout 测真实高度替代写死；超阈值改 ScrollView；收起态加 pointerEvents:none。
- 影响：体验（长详情缺失、偶发误触）、正确性 bug。
- 来源：交互 #3

**M18 — 弹窗缺常驻关闭入口 / CTA 埋滚动底 / 编辑点遮罩静默丢数据**
- 界面：`DietPlanLogicModal.tsx` + 首页 `DashboardMetricDetailModal`/`CustomMealAdjustmentModal`/`MealTextEditorModal`/`FoodTagEditorModal`
- 现象：仅 fade 入场无常驻 X；底部 CTA 在 maxHeight:85% ScrollView 内需滚才触达；`FoodTagEditorModal` 点遮罩直接关闭且静默丢弃未保存的 label/calories。
- 依据：弹窗退出路径应始终可见；编辑类"点外面即丢数据"违防错/可撤销。
- 建议：头部常驻"标题+关闭 X(≥44px)"；编辑类补"取消"+遮罩关闭前丢弃确认；入场改 slide/spring scale。
- 影响：体验（找出口困惑、编辑丢数据）、转化（弹窗内引导转化↓）。
- 来源：交互 #4

**M19 — LoadingToSuccess / Spinner 抖动 + 成功态不持久**
- 界面：`components/shared/LoadingToSuccess.tsx`(DefaultSpinner) + `EmptyState.tsx`(SpinningLoader)
- 现象：rotation 写在渲染体，父 re-render 时旋转从 0 重跳抖动；成功对勾 autoHideMs=800 后消失，宿主无持久态则"一闪而过"。
- 依据：微交互应稳定、状态应被确认。
- 建议：旋转 start 移入 useEffect 只跑一次(或 useDerivedValue)；成功态保留持久确认(文字/横条)而非纯消失；补 accessibilityLabel。
- 影响：体验（spinner 抖、成功无确认→不确定感）、信任（中）。
- 来源：交互 #5

**M20 — 多处硬编码 #F7FAFF 在日间模式文字不可见**
- 界面：`more.tsx`(L238/452 #F7FAFF, L238/518/691 #FFFFFF)、`index.tsx`(L2629 #FFFFFF)、`GlassTile.tsx`/`Button.tsx`/`Switch.tsx` 等多处硬编码近白
- 现象：日间(浅色)主题下，硬编码近白背景/文字与浅底对比不足，文字/控件不可见。
- 依据：主题一致性——颜色应走 `useThemeColors()`/`resolveThemeColor()`，禁止硬编码。
- 建议：全量替换硬编码色为主题 Token；加 lint 规则禁止裸 `#FFFFFF/#F7FAFF`；重点回归 more/index 日间模式。
- 影响：体验（日间模式可用性原则崩）、转化/留存（中-高，浅色用户直接不可用）。
- 来源：视觉

**M21 — DashboardGrid（含宏量环）死代码未接入**
- 界面：`components/diet/DashboardGrid.tsx`(支持 bullet/barCursor/kpiCards/rings 四式) + `DashboardCard.tsx`(图例)——grep 仅定义/导出，无 screen 引用
- 现象：已实现的"仪表盘可视化"能力（含宏量 rings）无任何界面消费；`more.tsx` 的 dashboardStyle 设置形同虚设。
- 依据：死代码 + 设置失效，既浪费又误导。
- 建议：见 C4/M13——把 rings 接入饮食看板（解宏量占比图）；或若永不上线则删除并移除 dashboardStyle 设置项。
- 影响：体验（设置无效）、维护（死代码）。
- 来源：视觉 + 营养 #20

**M22 — 营养表单位缺失与窄屏拥挤**
- 界面：营养来源详情表（kcal 无"kcal"单位标注、g 缺列头）；窄屏下列挤压换行
- 现象：数字无单位、窄屏挤成一团，减脂新手看不懂"1200 是什么"。
- 依据：可读性原则——数值必须带单位、窄屏需响应式列宽。
- 建议：每列补单位(g/kcal%)；窄屏改用两行堆叠或横向滚动且首列冻结；数值用 tabular-nums 对齐。
- 影响：体验（可读性）、转化（中）。
- 来源：营养 🟢→升 🟡（影响可读性）
